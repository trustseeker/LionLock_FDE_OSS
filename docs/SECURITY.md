# Security Policy

## Reporting Vulnerabilities
- Report privately through GitHub: open the repository's **Security** tab and choose **Report a vulnerability**. Only the maintainers can see the report.
- Please do not open a public issue for a suspected vulnerability.
- Include affected component, version (commit hash), and reproduction steps.
- Expect first response within 72 hours; coordinated disclosure is appreciated.

## Supported Versions
Security fixes go into the newest release on [PyPI](https://pypi.org/project/lionlock/), which is
currently in the 1.0 beta series. LionLock is beta software: interfaces may change before 1.0.0,
and no release is approved for production use. Pin an exact version (for example
`lionlock==1.0.0b2`) and read the [changelog](../CHANGELOG.md) before upgrading.

## Hardening Guidance
- Write logs to a directory with restrictive permissions; avoid world-writable paths.
- Rotate or archive trustvault logs regularly to keep auditing manageable.
- Check a log with `TrustVaultLogger.verify_chain()` before relying on it. The hash chain shows
  that records were not edited, reordered or removed in the middle. On its own it cannot show that
  the whole file was not rewritten, because anyone who can write the file can build a new, valid
  chain. To catch that, keep the latest chain head (its hash and record count) somewhere the log's
  writer cannot change, and compare against it. See [AUDIT_LOGGING.md](AUDIT_LOGGING.md).
- `tools/lockdown.sh` writes a SHA-256 manifest of the tree, plus an OpenTimestamps proof when the
  `ots` client is installed. A manifest shows whether files changed after it was made. It does not
  show who wrote them.

## Fernet Key Management & Rotation
Failsafe encryption uses Fernet from the `cryptography` library: AES-128 in CBC mode, with each
token authenticated by HMAC-SHA256.

### Key Storage
- Store the Fernet key in a secrets manager (AWS Secrets Manager, HashiCorp Vault, Azure Key Vault, or Kubernetes Secrets).
- Never commit keys to version control.
- Put the key in an environment variable, and set `failsafe.key_env` in `lionlock.toml` to that
  variable's name. The default name is `LIONLOCK_FAILSAFE_KEY_B64`.
- The key must be base64-encoded (as generated by `cryptography.fernet.Fernet.generate_key()`).

### Key Rotation Procedure
1. **Generate a new key** in your secrets manager:
   ```python
   from cryptography.fernet import Fernet
   new_key = Fernet.generate_key()  # Store this base64 string in your secrets manager
   print(new_key.decode('utf-8'))
   ```
2. **Update the secret** in your infrastructure (do NOT commit to code).
3. **Redeploy** applications pointing to the new key.
4. **Archive old encrypted events** (optional). LionLock only encrypts; to read old events,
   decrypt them with the old key using `cryptography.fernet.Fernet(old_key).decrypt(token)`, then
   destroy the old key.
5. **Test** failsafe behavior with the new key before destroying the old one.

### Monitoring Key Compromise
- If you suspect key compromise:
  1. Immediately revoke the old key in your secrets manager.
  2. Generate and deploy a new key.
  3. Audit all encrypted events written under the old key (they should be regenerated if needed).
  4. Notify your security team and review access logs for unauthorized access to the key.
- Each Fernet token records when it was created. LionLock never reads tokens back, so it never
  checks their age; check it yourself when you decrypt, if it matters to you.

## Telemetry
- Logging is local by default (`logs/lionlock.db`); uploads are opt-in and disabled by `DO_NOT_TRACK=1`.
- Uploads contain only the allowlisted fields in [TELEMETRY.md](TELEMETRY.md), sent and stored as files rebuilt from validated rows; the receiver re-applies the same policy and treats every snapshot as untrusted input.
- The receiver never logs client addresses, including in its handler error path, and refuses unsupported warehouse layouts without changing them.

## Privacy Trade-offs (OSS)
- Key-based scrubbing blocks known prompt/response field names.
- Value-based scanning rejects obvious markers (e.g., `prompt:` / `response=`) and large free-text strings.
- These checks are heuristic: they can miss short/unlabeled text and can reject long descriptive values.
- Avoid passing raw prompt/response text; hash, summarize, or redact upstream before logging.
- Canonical SQL writers for Module 05 events and missed-signal events enforce value scanning; other logs may only apply key-based scrubs.

## Security Checks
- Secret scanning: `bash tools/secret_scan.sh`
- Dependency audit: `bash tools/security_audit.sh` (requires `pip-audit` via `pip install -e '.[dev]'`)
- Policy: fix vulnerabilities when found; if a specific issue must be temporarily allowed, document it with rationale and date in an allowlist before suppressing.
- No secrets in the repository: rotate any leaked material immediately if detected.
